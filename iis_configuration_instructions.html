Understanding IIS Configuration for Angular

This guide explains how to configure Microsoft Internet Information Services (IIS) to serve your Angular Single-Page Application (SPA). The concepts are similar to NGINX but the implementation is different.

IIS Concepts: Sites and Bindings

In IIS, you don't use text files like nginx.conf for the main setup. Instead, you use the IIS Manager interface to create "Sites" and "Application Pools".

  • Site: A Site is the equivalent of an NGINX server block. It's the container for your website's content and settings.
  • Bindings: A Binding is the equivalent of NGINX's listen and server_name directives combined. It tells IIS which requests to direct to this specific site.

Site Bindings Explained

When you set up a site in IIS, you configure its bindings. A binding has three main parts:

  • IP Address: The specific server IP address to listen on. You can leave this as "All Unassigned" to accept traffic from any IP on the server.
  • Port: This is the equivalent of listen. For standard web traffic, you would set this to 80 for HTTP and 443 for HTTPS.
  • Host Name: This is the equivalent of server_name. IIS checks the request's Host header against this value. If a request for http://www.my-app.com comes in, IIS will route it to the site that has a binding with the host name "www.my-app.com".

To host two sites on the same IP and port, you would create two different Sites in IIS, each with a binding on port 80 but with different Host Names (e.g., "www.app-one.com" and "www.app-two.com").

Handling SPA Routing in IIS: The `web.config` File

Just like with NGINX, the biggest challenge is handling Angular's client-side routing. If a user requests /home, IIS will look for a file or folder named "home" and return a 404 error when it can't find one.

The solution is to use the URL Rewrite Module in IIS. This module allows you to create a rule that intercepts incoming requests and, if certain conditions are met, rewrites the request to point to your index.html file.

Important: The URL Rewrite Module is not installed on IIS by default. You may need to download and install it from Microsoft's website.

The Rewrite Rule in `web.config`

When you configure a rewrite rule, IIS saves it into a file named web.config in the root directory of your website's content. You can either use the IIS Manager to create the rule or place a `web.config` file with the following content directly into the same folder as your `index.html`.

This file is the direct equivalent of the try_files $uri $uri/ /index.html; line in NGINX.


<?xml version="1.0" encoding="UTF-8"?>
<configuration>
  <system.webServer>
    <rewrite>
      <rules>
        <rule name="Angular Routes" stopProcessing="true">
          <match url=".*" />
          <conditions logicalGrouping="MatchAll">
            <add input="{REQUEST_FILENAME}" matchType="IsFile" negate="true" />
            <add input="{REQUEST_FILENAME}" matchType="IsDirectory" negate="true" />
          </conditions>
          <action type="Rewrite" url="/" />
        </rule>
      </rules>
    </rewrite>
  </system.webServer>
</configuration>

Deeper Dive into `web.config`

The web.config file is the main configuration file for web applications running on IIS. It's a powerful XML file that allows you to control a wide range of server behaviors at a directory-specific level.

  • Hierarchical Configuration: A web.config file in a specific folder applies its settings to that folder and any sub-folders. This allows for granular control. A configuration in a sub-folder can override settings from a parent folder.
  • Broad Scope: While we are using it for URL rewriting, web.config can manage many other settings, including:
    • Custom error pages (e.g., showing a user-friendly 404 page).
    • Security settings like authentication and authorization rules.
    • MIME types, to tell browsers how to handle custom file extensions.
    • Request filtering and limits.
    • Application settings and connection strings for backend applications (more common in ASP.NET).
  • XML Structure: The root element is always <configuration>. Settings specific to the IIS web server itself are placed within the <system.webServer> section. This is why the <rewrite> rules for our Angular application live inside this section.

For a typical Angular deployment, the URL rewrite rule is the most critical part of the web.config. However, understanding its broader capabilities is useful if you need to apply more advanced server configurations to your application in the future.

How the Rule Works:

  1. <match url=".*" />: This tells the rule to look at every incoming request.
  2. <conditions>: The rule only proceeds if the following conditions are met:
    • <add input="{REQUEST_FILENAME}" matchType="IsFile" negate="true" />: The requested URL is NOT a real file on the server.
    • <add input="{REQUEST_FILENAME}" matchType="IsDirectory" negate="true" />: The requested URL is NOT a real directory on the server.
  3. <action type="Rewrite" url="/" />: If the conditions are met (meaning it's an Angular route and not a request for an asset like a CSS or image file), IIS internally rewrites the request to point to the root URL (`/`), which serves the index.html file.
