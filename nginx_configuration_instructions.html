Understanding Your NGINX Configuration for Angular

This guide explains the purpose of the nginx.conf file used to serve your Angular Single-Page Application (SPA), especially within a Docker container.

The server Block: A Virtual Host

Think of the server { ... } block as a blueprint for a single website. NGINX can host many websites on the same machine, and it uses server blocks to know how to handle traffic for each one. When a request comes into NGINX, its first job is to decide which of these blueprints to use.

This decision is primarily made using two directives: listen and server_name.

listen 80;

  • What it is: This directive tells NGINX to monitor a specific network "port" on the server for incoming connections. Port 80 is the universally recognized default port for all standard HTTP web traffic.
  • Why it's necessary: A server has thousands of ports to manage different services. By listening on port 80, NGINX declares itself as the primary handler for web requests. When you type http://some-address into your browser, the browser automatically connects to port 80.

server_name localhost;

  • What it is: This is the crucial directive NGINX uses to distinguish between different websites hosted on the same IP address and port. It tells NGINX: "This server block is responsible for traffic intended for the website named 'localhost'."
  • How it works: When your browser makes a request, it sends a Host header that specifies the domain name you typed in (e.g., Host: localhost). NGINX reads this header and matches it against the server_name in its available server blocks. If it finds a match, it uses the rules inside that block.
  • In a production scenario: You would change this to your public domain name, for example: server_name www.my-awesome-app.com;.

location / and try_files

This is the logic that makes your Angular app work behind a web server.

  • location / { ... }: This catches all incoming requests because every request URI starts with a /.
  • try_files $uri $uri/ /index.html;: This directive works in a sequence of three steps:
    1. $uri (Try as a file): NGINX looks for a file that exactly matches the request URI (e.g., /assets/logo.png). If found, it serves it. This is how your CSS, JS, and image assets are delivered.
    2. $uri/ (Try as a directory): If no file is found, NGINX checks if the URI matches a directory. This rarely succeeds for an Angular app.
    3. /index.html (The Fallback): If both checks fail (which they will for any Angular route like /home or /users), NGINX serves the index.html file. The Angular router then loads and interprets the URL to display the correct component.

Configuration Examples

Example 1: Single Server Configuration

This is a standard configuration for serving a single Angular application. It listens on port 80 for traffic intended for www.my-app.com and serves the application.


server {
    listen 80;
    server_name www.my-app.com;

    # Path to the root of your built Angular app
    root /var/www/my-app/html;
    index index.html;

    # Fallback for SPA routing
    location / {
        try_files $uri $uri/ /index.html;
    }
}

Example 2: Two-Server Configuration

This example shows how NGINX can serve two different websites from the same server. NGINX uses the server_name to decide which site to show.


# Configuration for the first application
server {
    listen 80;
    server_name www.app-one.com;

    root /var/www/app-one/html;
    index index.html;

    location / {
        try_files $uri $uri/ /index.html;
    }
}

# Configuration for the second application
server {
    listen 80;
    server_name www.app-two.com;

    root /var/www/app-two/html;
    index index.html;

    location / {
        try_files $uri $uri/ /index.html;
    }
}
